## 1. Scope: A Different Layer Than Ch240

Ch240 covers NVIDIA's Physical AI/Omniverse orchestration stack for robotics simulation and synthetic-data generation — Isaac Sim workloads scheduled onto NGC-container-based GPU clusters, purpose-built for that pipeline. This chapter covers the older and, for most VFX and animation studios, far more load-bearing infrastructure problem: keeping a shared USD asset database consistent across dozens of concurrently-editing artists, and dispatching millions of individual frame- and layer-level render tasks across a shared, multi-show compute pool with fair resource allocation between productions. Nucleus (§2) solves the first problem; OpenCue (§3) solves the second. Neither is NVIDIA-exclusive tooling in the way Ch240's stack is — OpenCue is vendor-neutral ASWF infrastructure that predates Omniverse by over a decade, and while Nucleus is an NVIDIA product, it interoperates with any USD-consuming client, Kit-based or not, via an open wire protocol (§2.3). The chapter closes with the deployment layer the two increasingly share: NGC containers and Kubernetes GPU scheduling (§6), which is the same substrate Ch240 covers for Physical AI workloads, applied here to conventional frame-parallel VFX/animation dispatch instead.

## 2. Nucleus: Live, Collaborative USD Asset Management

### 2.1 What Nucleus Is

Omniverse Nucleus is described in NVIDIA's own documentation as "the database and collaboration engine of Omniverse," enabling multiple users connected through different client applications to work on the same USD-based scene data simultaneously. [Source: NVIDIA Omniverse Nucleus documentation, https://docs.omniverse.nvidia.com/nucleus/latest/index.html] Nucleus is not a render manager — it has no concept of a job, layer, or frame in the OpenCue sense (§3) — it is a versioned, collaborative asset store that sits *beneath* whatever render manager a studio dispatches work through. A render farm reading USD stages from Nucleus and a render farm reading the same stages from a conventional shared filesystem are functionally interchangeable from OpenCue's perspective; Nucleus's value is upstream of the farm, in keeping the asset graph an artist is actively editing consistent with the asset graph a render job checks out.

### 2.2 Publish/Subscribe and Live Editing

Nucleus operates on a publish/subscribe model: clients publish modifications to USD data to the Nucleus database, or subscribe to changes made by others, subject to access control. [Source: NVIDIA Omniverse Nucleus documentation, https://docs.omniverse.nvidia.com/nucleus/latest/index.html] The **OmniLive** live-sync feature layers real-time collaborative editing on top of this model: "changes are transmitted in real-time between connected third-party applications," letting multiple users author geometry, lighting, materials, and other scene data in the same USD stage from different client applications simultaneously. [Source: NVIDIA Omniverse Nucleus Features documentation, https://docs.omniverse.nvidia.com/nucleus/latest/features.html] Client connectivity assumes two fixed ports in a standard deployment: the Nucleus Core API on port 3009, and Nucleus Discovery — the service through which other Nucleus services register and advertise themselves to clients — on port 3333. [Source: NVIDIA Omniverse Nucleus Architecture documentation, https://docs.omniverse.nvidia.com/nucleus/latest/architecture.html] Nucleus represents assets in a hierarchical, filesystem-like tree of forward-slash paths (e.g. `/Users/jdoe/myfile.usd`), and Enterprise deployments add a dedicated Large File Transfer (LFT) Service exposing an HTTP endpoint for large-file upload/download, which can itself be horizontally scaled to more than one instance. [Source: NVIDIA Omniverse Nucleus Architecture documentation, https://docs.omniverse.nvidia.com/nucleus/latest/architecture.html]

### 2.3 Checkpoints: Automatic Versioning

Every write to Nucleus is checkpointed. NVIDIA's documentation states that checkpoints "are created atomically when a file operation occurs," giving every save an implicit, automatically-managed version history without an artist needing to invoke a separate version-control step. [Source: NVIDIA Omniverse Nucleus Features documentation, https://docs.omniverse.nvidia.com/nucleus/latest/features.html] This is distinct from live-layer editing (§2.2): OmniLive propagates *in-progress, uncommitted* edits between connected clients in real time over the live session, while a checkpoint is a durable, addressable version of the asset that persists after the session ends and can be reverted to independently of what any other connected client is currently doing. The client-side operation for creating and branching checkpoints is exposed through the Omni Client Library (§2.4) as `OmniClientBranchAndCheckpoint`. [Source: NVIDIA Omniverse Client Library documentation, https://docs.omniverse.nvidia.com/kit/docs/client_library/latest/index.html]

### 2.4 The Omni Client Library and REST Access

Non-Kit clients — a render-farm frame-check script, a custodial asset-management tool, a CI pipeline validating a USD stage before it reaches the farm — do not need to embed a full Omniverse Kit application to talk to Nucleus. The **Omniverse Client Library** is NVIDIA's own description of "the library that all Omniverse clients should use to communicate with Omniverse servers," shipping both a native C API (`OmniClient.h`) and Python bindings around the same underlying operations: `omniClientList`, `omniClientRead`, `omniClientWrite`, ACL and lock management, and checkpoint/branch operations. [Source: NVIDIA Omniverse Client Library documentation, https://docs.omniverse.nvidia.com/kit/docs/client_library/latest/index.html] The library's Nucleus provider implements the custom `omniverse://` URI scheme for addressing files on a Nucleus server, and is documented as the only provider that supports live mode — i.e. the OmniLive subscription semantics of §2.2 are a Nucleus-specific capability, not a generic feature of every URI scheme the client library supports. [Source: NVIDIA Omniverse Client Library documentation, https://docs.omniverse.nvidia.com/kit/docs/client_library/latest/index.html] Alongside the client library, NVIDIA publishes a set of gRPC and REST API specifications and microservice adapters intended to let Nucleus-adjacent functionality integrate with existing storage and infrastructure services — the `omni.services.usd.base` REST API is one such published surface. [Source: NVIDIA Omniverse documentation hub, https://docs.nvidia.com/omniverse/index.html] For a render-farm engineer, the practical distinction is: a Kit-based render delegate or DCC plug-in typically talks to Nucleus through the client library embedded in Kit itself, while a non-Kit render-management tool (a custom OpenCue submission wrapper, for instance) is more likely to shell out to the client library's C/Python API directly, or to a REST/microservice adapter, rather than reimplementing the `omniverse://` protocol from scratch.

### 2.5 Nucleus Navigator

**Nucleus Navigator** is Nucleus's web-based content browser: after authentication, it lets users browse Nucleus-hosted content, manage permissions, upload or download files, and share direct URLs into the asset tree from any web browser, without requiring the requester to have an Omniverse client installed. [Source: NVIDIA Omniverse Nucleus Navigator documentation, https://docs.omniverse.nvidia.com/nucleus/latest/config-and-info/navigator_v3.html] For a render farm, Navigator is the operational tool most likely to be used by a pipeline TD confirming that a specific checkpointed version of an asset landed correctly, or by an artist sharing a link to a specific USD layer with a collaborator who doesn't run Omniverse locally — it sits alongside CueGUI (§3.3) as one of the two web/GUI surfaces a studio's render-farm operators touch day to day, one for asset state, one for job state.

### 2.6 On-Premises vs Cloud Deployment Topologies

Nucleus supports deployment "on-premises using an Enterprise Nucleus Server, or on your preferred Cloud Service Provider" under a bring-your-own-license model, running on bare-metal Linux hardware or under virtualization (VMware, Hyper-V). [Source: NVIDIA Omniverse Nucleus Features documentation, https://docs.omniverse.nvidia.com/nucleus/latest/features.html] Cloud deployment is distributed as containers published on NVIDIA NGC, deployable to public clouds including AWS and Azure; NVIDIA's own framing of the cloud topology emphasizes self-healing infrastructure, streamlined SSL/TLS certificate management, and on-demand scalability as the benefits over a fixed on-premises install. [Source: NVIDIA Omniverse Cloud Services announcement, https://nvidianews.nvidia.com/news/nvidia-launches-omniverse-cloud-services-for-building-and-operating-industrial-metaverse-applications] Nucleus does not require GPU hardware at all for CPU-only deployments — it is a database and file-service workload, not a rendering workload — but NVIDIA licensing still requires one Omniverse Enterprise / NVIDIA AI Enterprise license per compute instance running Nucleus, GPU-equipped or not. [Source: NVIDIA Developer Forums, Nucleus Server deployment clarification thread, https://forums.developer.nvidia.com/t/clarification-on-the-future-direction-deployment-requirements-and-licensing-of-omniverse-nucleus-server/370554] A studio choosing between topologies is trading the same variables as any other centralized-asset-server decision: on-prem keeps checkpoint and live-sync traffic on the local network closest to artist workstations and the render farm's storage, minimizing round-trip latency for the interactive live-editing case (§2.2); cloud deployment trades that latency for elastic capacity and offloaded infrastructure management, at the cost of every artist edit and every farm asset fetch crossing a WAN link to the cloud region hosting Nucleus.

NVIDIA's own guidance draws an explicit production-readiness line that a render-farm engineer evaluating Nucleus should weigh directly: officially, Nucleus "is not designed for high availability" — backup and restore tooling exists, but there is no instant automatic failover between redundant Nucleus instances, a materially different guarantee than the multi-master or automatic-failover topologies expected of a database backing continuous, deadline-driven production render dispatch. [Source: NVIDIA Developer Forums, Nucleus Server deployment clarification thread, https://forums.developer.nvidia.com/t/clarification-on-the-future-direction-deployment-requirements-and-licensing-of-omniverse-nucleus-server/370554] §7.5's Roadmap discussion returns to this point alongside a second, related fact from the same NVIDIA forum response: Nucleus feature development itself has been paused in favor of a newer Storage APIs / services-adapter architecture intended to eventually reach feature parity — a status any studio standing up new Nucleus infrastructure today should factor into a multi-year deployment plan.

## 3. OpenCue: The Academy Software Foundation's Reference Render Manager

### 3.1 Origins and Governance

OpenCue originated as Sony Pictures Imageworks' in-house render manager, used in production on hundreds of films before the studio open-sourced it. [Source: OpenCue GitHub repository, https://github.com/AcademySoftwareFoundation/OpenCue] It is now a Academy Software Foundation (ASWF) project, distributed under the Apache License 2.0 — placing it in the same governance family as Open Shading Language and OpenPGL, the two ASWF sibling projects covered in Ch247, and reflecting the same industry pattern: a studio-internal tool, battle-tested on real productions, donated to a neutral foundation to become shared infrastructure rather than a single studio's proprietary advantage. [Source: OpenCue GitHub repository, https://github.com/AcademySoftwareFoundation/OpenCue]

### 3.2 Cuebot and RQD: The Two Halves of the Architecture

OpenCue's architecture splits cleanly into a central management service and a per-host worker daemon. **Cuebot** is described in OpenCue's own documentation as "a utility that runs in the background on a workstation and performs a variety of important OpenCue management tasks," and — critically for farm-scale deployment — "Cuebot can also run in a server cluster for high availability." [Source: OpenCue documentation, Concepts overview, https://github.com/AcademySoftwareFoundation/opencue.io/blob/master/content/docs/Concepts/opencue-overview.md] Cuebot is the central management server: it manages job submissions, distributes work to render nodes, and responds to API requests from client tools. [Source: OpenCue documentation glossary, https://docs.opencue.io/docs/concepts/glossary/] **RQD** — the Render Queue Daemon — is the software daemon that runs on every rendering host doing work for an OpenCue deployment: RQD registers its host with Cuebot, receives work instructions, monitors the worker processes it spawns to execute frames, and reports results back to Cuebot. [Source: OpenCue documentation, Concepts overview, https://github.com/AcademySoftwareFoundation/opencue.io/blob/master/content/docs/Concepts/opencue-overview.md; OpenCue documentation glossary, https://docs.opencue.io/docs/concepts/glossary/] This Cuebot/RQD split is architecturally the same pattern every render manager surveyed in §4 uses under different names — a central scheduler holding the queue and state, and a lightweight per-node agent that pulls or receives work — but OpenCue's version is the one with fully open, ASWF-governed source on both sides of that split.

### 3.3 CueGUI and CueSubmit

Artists interact with OpenCue through two GUI tools rather than the Cuebot/RQD internals directly. **CueSubmit** is "a graphical user interface for configuring and launching rendering jobs to an OpenCue deployment," typically run as a plug-in embedded in an artist's 3D application so a render can be submitted without leaving the DCC. [Source: OpenCue documentation, Concepts overview, https://github.com/AcademySoftwareFoundation/opencue.io/blob/master/content/docs/Concepts/opencue-overview.md] **CueGUI** is the graphical interface artists and render-wranglers use to monitor and manage jobs already in the queue — inspecting per-frame status, retrying or killing failed frames, and adjusting job priority — and its CueCommander mode extends this into farm administration: navigating shows, allocations, subscriptions, monitored hosts, and services. [Source: OpenCue documentation, Concepts overview, https://github.com/AcademySoftwareFoundation/opencue.io/blob/master/content/docs/Concepts/opencue-overview.md; OpenCue documentation, CueCommander Administration Guide, https://docs.opencue.io/docs/user-guides/cuecommander-administration-guide/] A newer web-based alternative, OpenCueWeb (CueWeb), exposes overlapping job-monitoring and administration functionality through a browser rather than a desktop GUI client. [Source: OpenCue documentation, OpenCueWeb System, https://docs.opencue.io/docs/other-guides/cueweb/] Programmatic access below the GUI layer goes through **PyCue**, OpenCue's Python client API for scripting job submission and queue queries, and **PyOutline**, the Python library for constructing the job/layer/frame graph (§3.4) that CueSubmit and custom submission tooling both build on.

### 3.4 The Job/Layer/Frame Hierarchy

OpenCue organizes all work into a strict three-level hierarchy. A **show** groups related work — all jobs submitted to OpenCue exist within a show, which is also the unit that a **subscription** (§3.5) attaches resource entitlement to. [Source: OpenCue documentation glossary, https://docs.opencue.io/docs/concepts/glossary/] A **job** is "a collection of layers, which is sent as a script to the queue to be processed on remote cores" — the top-level unit of dispatch, corresponding to one submission (a shot's beauty render, a simulation pass, a full-sequence comp). [Source: OpenCue documentation glossary, https://docs.opencue.io/docs/concepts/glossary/] A **layer** is a sub-job within that job's outline script: each layer carries its own frame range and a specific command to execute — a render layer, a denoise layer, and a Cryptomatte-extraction layer within the same job would typically be three separate layers, each with independent resource requirements and its own tag (§3.5). [Source: OpenCue documentation glossary, https://docs.opencue.io/docs/concepts/glossary/] A **frame** is a single command instance within a layer — the atomic unit of dispatch, typically one image frame's worth of render work, though nothing in the model requires a one-to-one mapping to a literal animation frame. [Source: OpenCue documentation glossary, https://docs.opencue.io/docs/concepts/glossary/] This three-level split is what lets OpenCue represent both frame-parallel dispatch (§5) and heterogeneous multi-stage pipelines (render → denoise → publish) within a single job object, rather than requiring a studio to chain together several independent job submissions with manual dependency tracking between them.

### 3.5 The Allocation/Subscription Resource Model

Multi-show farm sharing — the problem of letting several productions draw from one physical compute pool fairly, without one show's burst of deadline-driven submissions starving another's day-to-day work — is handled by a two-object model sitting above jobs. An **allocation** is "a group for organizing render hosts by associating them with a facility and a tag" — the pool of physical machines a farm administrator carves out, typically by hardware class, site, or licensing constraint. [Source: OpenCue documentation glossary, https://docs.opencue.io/docs/concepts/glossary/] A **subscription** is "an object that associates multiple allocations with a show," and it is this object — not the allocation directly — that "drives what render hosts can do work for a show": each subscription defines how many resources (procs, i.e. cores/slots) the associated show is entitled to draw from that allocation. [Source: OpenCue documentation glossary, https://docs.opencue.io/docs/concepts/glossary/; OpenCue documentation, Concepts overview, https://github.com/AcademySoftwareFoundation/opencue.io/blob/master/content/docs/Concepts/opencue-overview.md] A **proc** is "a slot on a render host that has been carved out and isolated to execute a frame," and a **host** is simply a machine running an RQD instance, which subdivides its own capacity into procs. [Source: OpenCue documentation glossary, https://docs.opencue.io/docs/concepts/glossary/] Finally, **tags** — arbitrary strings assignable to both a host and a layer — provide the routing mechanism underneath allocations: "frames contained in a layer with a tag will only render on a host that also shares that tag," which is how a studio pins GPU-heavy layers to GPU-equipped hosts, or licensing-constrained layers to the subset of hosts holding a floating license seat. [Source: OpenCue documentation glossary, https://docs.opencue.io/docs/concepts/glossary/] Put together: allocations are how a farm administrator partitions physical capacity, subscriptions are how that capacity is entitled out per-show, and tags are how work within a show is routed to the correct subset of a host pool once entitled — three orthogonal controls a farm administrator tunes independently as shows start, wrap, and compete for the same underlying hardware.

## 4. The Closed Alternatives: Tractor, Deadline, Qube

OpenCue's job/layer/frame and allocation/subscription model is not the only design point in this space; it is the open, ASWF-governed answer to a problem three commercial products have solved with broadly similar central-scheduler/per-node-agent architectures for longer. This section stays qualitative where public documentation is thin, per the general convention that closed-product internals not independently verifiable from primary sources are described at the level the vendor's own public documentation supports, not extrapolated further.

### 4.1 Pixar Tractor

Tractor, Pixar's render manager, splits into three components with clear analogues to OpenCue's own split: **tractor-engine**, which maintains the central job queue and dispatches tasks (Pixar's own material describes it as capable of dispatching over 500 tasks per second) and is the direct counterpart to Cuebot; **tractor-blade**, a Python-based execution server running on each render node — the counterpart to RQD, with the notable difference that Tractor explicitly documents blades as extensible via custom Python modules system administrators install to customize task execution; and **tractor-dashboard**, a customizable web browser UI for centralized job monitoring, the counterpart to CueGUI/CueWeb. [Source: Pixar RenderMan, Tractor Render Management, https://renderman.pixar.com/tractor] Recent Tractor releases have added a blade patch-management system that pushes new blade software versions out across the farm automatically, and a "Profiles" mechanism letting a blade advertise different capabilities depending on which commands it has previously been asked to run. [Source: Pixar RenderMan, Tractor Getting Started documentation, https://rmanwiki.pixar.com/display/TRA/Getting+Started] Tractor is licensed commercially through Pixar/RenderMan channels rather than under an open-source license, and its source is not publicly auditable the way OpenCue's or OSL's is.

### 4.2 AWS Thinkbox Deadline

Deadline's architecture centers on a shared **Repository** — containing plugins, scripts, logs, and job auxiliary files — that **Worker** nodes pull configuration from at startup, an optional **Pulse** service that performs farm maintenance (auto-configuration, power management, worker throttling, statistics gathering, and a web service), and a Monitor client artists use to submit and track jobs. [Source: AWS Thinkbox Deadline 10.4 documentation, Pulse, https://docs.thinkboxsoftware.com/products/deadline/10.4/1_User%20Manual/manual/pulse.html; AWS Thinkbox Deadline 10.4 documentation, Overview, https://docs.thinkboxsoftware.com/products/deadline/10.4/1_User%20Manual/manual/overview.html] Deadline was made available free of charge after AWS's 2017 acquisition of Thinkbox, and — most relevant to a render-farm engineer evaluating it today — AWS announced that Deadline 10 entered **maintenance mode** on November 7, 2025: the software remains fully supported and installable, and existing farms continue to operate and can still add render nodes exactly as before, but AWS has redirected active feature development entirely to **Deadline Cloud**, its newer, fully-managed cloud render-farm service launched in 2024, which eliminates self-managed repositories, databases, and license servers in favor of AWS-operated infrastructure. [Source: CG Channel, "AWS to put Deadline into maintenance mode next month", https://www.cgchannel.com/2025/10/aws-to-put-deadline-into-maintenance-mode-next-month/] For a studio choosing a render manager today, this is a directly comparable inflection point to the RenderMan RIS→XPU transition Ch247 §1.2 covers in detail: an established on-premises product entering feature-frozen maintenance while the vendor's investment moves to a different (in Deadline's case, cloud-hosted) architecture is exactly the kind of transition that makes OpenCue's vendor-neutral, self-hosted, actively-developed governance model a materially different risk profile — a studio standardizing on OpenCue is not exposed to a single vendor's decision to sunset an on-premises product line in favor of a cloud offering.

### 4.3 PipelineFX Qube!

Qube! follows the same three-part shape once more: a **Supervisor** — always run on a dedicated machine — that queues and dispatches jobs and decides which jobs run on which workers; **Clients**, which submit jobs to the Supervisor; and **Workers**, the execution hosts that actually process render jobs once dispatched. [Source: PipelineFX, How Qube Works, https://www.pipelinefx.com/how-qube-works/] Licensing in Qube! is centralized at the Supervisor: the Supervisor is both the license server and the sole consumer of worker licenses, which are keyed to the Supervisor's MAC address, with one license consumed per worker actively running a job. [Source: PipelineFX, How Qube Works, https://www.pipelinefx.com/how-qube-works/] Public technical documentation on Qube!'s newer releases is comparatively sparse relative to Tractor's and Deadline's; readers evaluating a current Qube! deployment should treat the architecture description above — which matches publicly available material as of this writing — as accurate to Qube!'s long-standing design rather than to any specific current release, and verify version-specific behavior against PipelineFX's own current documentation directly.

### 4.4 The Common Shape, and What OpenCue Displaces

All three commercial products and OpenCue converge on the same two-tier shape: a central scheduler holding job/queue state (Cuebot, tractor-engine, Deadline's Repository+Pulse, Qube!'s Supervisor) and a per-host worker agent (RQD, tractor-blade, Deadline Worker, Qube! Worker) that registers with the scheduler and executes dispatched work. What differs is licensing model, source availability, and — as of the Deadline maintenance-mode announcement and Tractor and Qube! remaining closed-source commercial products — which of these a studio can audit, extend, or fork without a vendor relationship. OpenCue is the only member of this set that is simultaneously free, source-available under a permissive license, and under active multi-studio ASWF governance rather than a single vendor's roadmap — the combination most VFX/animation studios standardizing render-farm infrastructure today are weighing Deadline's and Qube!'s commercial support and Tractor's RenderMan-native integration against.

## 5. Frame-Parallel vs Tile-Parallel Distributed Rendering

### 5.1 Frame-Parallel: OpenCue's Native Model

The job/layer/frame hierarchy in §3.4 is a **frame-parallel** distribution model: a shot's frame range is subdivided, and each frame — or, for simulation-heavy layers, a small chunk of consecutive frames — is dispatched as one independent unit of work to one proc on one host. Each frame renders as a complete, self-contained image from start to finish on the machine it lands on; no communication between hosts is required during that frame's render, only before dispatch (checking out the scene/asset state) and after completion (publishing the finished frame). This is the model OpenCue, Tractor, Deadline, and Qube! all target natively, and it is also the model that makes the allocation/subscription/tag machinery of §3.5 sufficient on its own: because frames are independent, a farm scheduler only needs to solve a bin-packing problem (which idle proc, matching which tag, should pick up which queued frame next), not a co-scheduling problem across multiple hosts working on the same output.

### 5.2 Tile-Parallel: Splitting a Single Frame

**Tile-parallel** (also called bucket-parallel) rendering instead splits one frame into rectangular regions — buckets or tiles — and distributes those regions across multiple compute units, which recombine into the final frame once all tiles complete. The technique reduces the working-set memory footprint per compute unit, since a tile only needs the geometry, textures, and acceleration structures touching its own screen-space region loaded rather than the whole frame's data, and it is the only viable strategy for interactive or near-real-time single-frame turnaround where frame-parallel dispatch (needing an entire farm's worth of frames in flight to show throughput) has nothing to distribute. [Source: General industry reference — bucket vs. progressive rendering, iRender knowledge base, https://irendering.net/know-bucket-and-progressive-rendering-in-redshift/] Tile-parallel rendering operates at a finer grain than frame-parallel dispatch and is typically implemented *within* a single renderer's own execution model (GPU-side bucket scheduling, or a distributed-framebuffer architecture spanning multiple machines for very large frames) rather than by the farm's job scheduler, since recombining tiles into a correct final image requires tighter coordination — consistent camera/light state across every tile-rendering unit, and a merge step — than a farm scheduler's frame-independent dispatch model assumes.

### 5.3 A Third, Distinct Layer: Device-Level Multi-GPU Parallelism

Ch69 covers a third form of parallelism that is easy to conflate with tile-parallel rendering but operates at a different layer entirely: NCCL-style work partitioning *within a single machine's* multiple GPUs, coordinating device-to-device data movement (denoiser feature buffers, cross-GPU acceleration-structure builds, gradient or radiance-estimate reduction) over NVLink or PCIe rather than over a farm network. That device-level partitioning is invisible to OpenCue's scheduler — from Cuebot's perspective, a multi-GPU render layer is still one frame occupying one proc on one host, however many GPUs that host's RQD-launched render process fans work out across internally. Frame-parallel dispatch (§5.1) is the farm-scheduler layer; tile-parallel dispatch (§5.2) is typically a within-renderer or within-job coordination layer, sometimes spanning several machines for a single very large frame; multi-GPU work partitioning (Ch69) is a within-host device layer beneath both. A studio's practical dispatch strategy usually composes at least the first and third: OpenCue frame-parallel dispatch across the farm, with each individual frame's render internally exploiting whatever multi-GPU parallelism the host it lands on provides — three genuinely distinct layers of "parallel rendering," not three names for the same idea.

## 6. NGC Containers and Kubernetes for Render Nodes

### 6.1 Containerizing RQD

OpenCue publishes a default RQD container image on Docker Hub that deliberately ships with no rendering software installed — it is a bare RQD daemon image, meant to be extended. [Source: OpenCue documentation, Customizing RQD rendering hosts, https://docs.opencue.io/docs/other-guides/customizing-rqd/] OpenCue's own `samples/rqd/` directory in the project repository provides worked Dockerfile examples, including one installing Blender as the render application layered on top of the base RQD image. [Source: OpenCue documentation, Customizing RQD rendering hosts, https://docs.opencue.io/docs/other-guides/customizing-rqd/] For GPU rendering specifically, OpenCue documents a sample CUDA Dockerfile that "extends the default RQD container image to support GPU rendering on supported Nvidia hardware," with the explicit prerequisite that the host running the container have the NVIDIA Container Toolkit installed so the container can access the GPU device at all. [Source: OpenCue documentation, Customizing RQD rendering hosts, https://docs.opencue.io/docs/other-guides/customizing-rqd/] The documentation's own worked example replaces a plain `image: opencue/rqd` reference in a Docker Compose file with a `build:` stanza pointing at the studio's extended Dockerfile — and explicitly notes that "for a production system, you might make a similar change to update the configuration files for a container management platform, such as Kubernetes," without providing turnkey Kubernetes manifests itself. [Source: OpenCue documentation, Customizing RQD rendering hosts, https://docs.opencue.io/docs/other-guides/customizing-rqd/] A studio deploying RQD via Kubernetes is therefore building that manifest itself on top of the same container-image pattern OpenCue documents for Docker Compose — one RQD-plus-renderer image per render application/version combination the farm needs to support, scheduled as a Kubernetes pod exposing GPU resources.

### 6.2 GPU Operator and GPU Feature Discovery

Once RQD render nodes run as Kubernetes pods rather than bare-metal or VM hosts, GPU provisioning becomes a cluster-management problem the NVIDIA GPU Operator is built to solve. The GPU Operator "uses the operator framework within Kubernetes to automate the management of all NVIDIA software components needed to provision GPUs" — the NVIDIA driver itself (to enable CUDA), the Kubernetes device plugin that exposes GPUs as a schedulable resource, the NVIDIA Container Toolkit RQD's own CUDA Dockerfile depends on (§6.1), and DCGM-based GPU health monitoring. [Source: NVIDIA GPU Operator documentation, https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/index.html] The Operator bundles **GPU Feature Discovery (GFD)** as automatic node labeling — attaching Kubernetes node labels describing each node's actual GPU model, memory, and driver/CUDA version — which is what lets a render-farm's Kubernetes scheduler place a tagged layer (§3.5's OpenCue tag concept, reimplemented at the Kubernetes-scheduling layer via node selectors/affinity rules against GFD's labels) on a node with the correct GPU class, the same routing problem OpenCue's tags solve at the Cuebot/RQD layer, solved a second time at the container-orchestration layer beneath it. [Source: NVIDIA GPU Operator documentation, https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/index.html] The GPU Operator itself is distributed as a Helm chart deployable to any GPU-provisioned Kubernetes cluster. [Source: NVIDIA GPU Operator documentation, Installing the NVIDIA GPU Operator, https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/getting-started.html] This is precisely the substrate Ch240 covers for NVIDIA's Physical AI orchestration workloads — GPU Operator plus GFD provisioning a Kubernetes cluster for Isaac Sim-driven simulation jobs. Here the same substrate provisions Kubernetes-scheduled RQD render nodes instead: the orchestration layer is identical, and only the workload dispatched onto it — a Physical AI simulation container versus a conventional VFX/animation RQD-plus-renderer container — differs between the two chapters.

## Roadmap

### Near-term (6–12 months)

- **Deadline 10's maintenance-mode window is now open.** As of November 7, 2025, AWS has stopped feature development on self-hosted Deadline 10 in favor of Deadline Cloud; existing farms continue to function and can still add render nodes, but studios evaluating render-manager choice today are choosing between an actively-developed OpenCue, a cloud-only Deadline Cloud, and Deadline 10's now-frozen feature set. [Source: CG Channel, "AWS to put Deadline into maintenance mode next month", https://www.cgchannel.com/2025/10/aws-to-put-deadline-into-maintenance-mode-next-month/]
- **Nucleus feature development is officially paused pending a Storage-APIs replacement.** Per NVIDIA's own forum guidance, Nucleus continues to receive security patches but no new features, while NVIDIA builds out a Storage APIs and services-adapter stack intended to eventually reach feature parity; studios standing up new Nucleus infrastructure in this window should plan around that stated trajectory rather than assuming continued Nucleus-specific feature investment. [Source: NVIDIA Developer Forums, Nucleus Server deployment clarification thread, https://forums.developer.nvidia.com/t/clarification-on-the-future-direction-deployment-requirements-and-licensing-of-omniverse-nucleus-server/370554]

### Medium-term (1–3 years)

- **Whether NVIDIA's Storage APIs stack actually reaches Nucleus feature parity is the open question for studios relying on Nucleus's live-editing and checkpoint model.** If the replacement stack lands with parity, the on-prem/cloud deployment trade-off in §2.6 carries forward largely unchanged onto new infrastructure; if it does not, studios with heavy OmniLive collaborative-editing dependence face a harder migration decision than a simple version upgrade. [Source: NVIDIA Developer Forums, Nucleus Server deployment clarification thread, https://forums.developer.nvidia.com/t/clarification-on-the-future-direction-deployment-requirements-and-licensing-of-omniverse-nucleus-server/370554]
- **Kubernetes-scheduled render farms are still a bring-your-own-manifest exercise.** OpenCue's own documentation stops at Docker Compose and explicitly defers Kubernetes deployment specifics to the studio; as GPU Operator/GFD-provisioned clusters become more common for the Physical AI workloads Ch240 covers, the tooling gap for turnkey Kubernetes-native RQD deployment (Helm charts, operator-managed RQD pods with GFD-aware scheduling built in) is a plausible area for either ASWF or community contribution to close. [Source: OpenCue documentation, Customizing RQD rendering hosts, https://docs.opencue.io/docs/other-guides/customizing-rqd/]

### Long-term

- **OpenCue's position as the only free, source-available, actively multi-studio-governed render manager in this comparison set is likely to strengthen rather than weaken.** With Deadline 10 in maintenance mode and Tractor and Qube! remaining single-vendor commercial products, OpenCue's ASWF governance model — the same structural advantage Ch247 attributes to OSL and OpenPGL's ASWF status over proprietary shading and guiding alternatives — is the version of this trade-off least exposed to any single vendor's roadmap decision, a pattern consistent with the broader ASWF thesis that shared, foundation-governed infrastructure outlasts studio-internal or single-vendor tooling in exactly this kind of transition window.
